# src/core — .NET 10 core

## Projects

Solution: `Normetry.slnx` at the repo root. Shared build settings live in the root `Directory.Build.props` (net10.0, nullable, warnings as errors) and package versions in `Directory.Packages.props` (central package management: `PackageReference` items carry no `Version`).

- `Normetry.BuildingBlocks` — shared primitives with no Normetry, EF Core or ASP.NET Core dependency. `Cqrs/` holds the in-house dispatcher (ADR 009): commands, queries, handlers, `IDispatcher`, pipeline behaviors (logging, FluentValidation) and `AddDispatcher(...)`, which scans for handlers and validators. `Results/` holds `Result`, `Result<T>` and `Error` for expected failures; `Normetry.Api` maps a failed result to ProblemDetails with `ToProblemDetails()`.
- `Normetry.Domain` — entities, value objects, domain events. References only BuildingBlocks: no EF Core, ASP.NET Core or dispatcher.
- `Normetry.Application` — commands, queries, handlers and validators, one folder per bounded context. References Domain and BuildingBlocks.
- `Normetry.Infrastructure` — EF Core (Npgsql), outbox, messaging, blob storage; implements Application abstractions. References Application.
- `Normetry.Migrations` — EF Core migrations only, in `Schema/` (structure, RLS, grants) and `Data/` (rows every environment needs; rules in `Data/README.md`), one history. A short-lived console app (`CoreMigrator`) the AppHost runs as `core_owner` before the API starts; see "Database migrations" in the root `CLAUDE.md`. References Infrastructure; nothing references it except the AppHost and the tests.
- `Normetry.Api` — composition root: endpoints, OIDC/JWT auth, YARP `/ai/*`, SignalR hubs, rate limiting. References Application, Infrastructure and ServiceDefaults.
- `Normetry.ServiceDefaults` — Aspire service defaults: OpenTelemetry, health checks (`/health`, `/alive`, Development only), service discovery, HTTP resilience.
- `Normetry.AppHost` — Aspire orchestration of every service and container. DCP and the dashboard come from NuGet (`AspireUseCliBundle=false`), so no Aspire CLI install is needed.

Layer dependencies are enforced by NetArchTest (`tests/Normetry.ArchitectureTests`). When a rule fails, fix the dependency, not the rule. A reference pointing up the layers (for example Domain → Infrastructure) is already rejected by MSBuild as a circular reference; the tests catch leaks such as EF Core or ASP.NET Core types in Domain.

Bounded contexts: Tenancy & Identity, Establishments, Documents, Regulations (read-only here), Assessments, Usage & Budget, Notifications.

## Persistence

- Schema `core` only, through EF Core migrations. Never touch `ai.*`.
- `CoreDbContext` (`Normetry.Infrastructure/Persistence`) uses Npgsql with EFCore.NamingConventions, so every table, column, key and index name is lower-case snake_case (`core.establishments.tenant_id`, `pk_establishments`). The history table keeps its name, `core."__EFMigrationsHistory"`, but its columns are snake_case too (`migration_id`, `product_version`).
- Tenant-owned tables follow the `rls-table` skill. Handlers never set the tenant and never filter by it: they go through repositories (interfaces in Application, EF Core in Infrastructure) and RLS returns only the current tenant's rows.
- No SQL reaches tenant data without a tenant (fail closed). Every runtime context is built with `UseTenantScopedCoreDatabase(connectionString, ITenantContext)`; `UseCoreDatabase`, which has no interceptors, is internal and visible only to `Normetry.Migrations`. The tenant-scoped builder adds two interceptors: `TenantTransactionInterceptor` runs `set_config('app.tenant_id', <tenant>, true)` as the first statement of every transaction EF Core starts or adopts (and throws when that transaction or session already holds another tenant), and `TransactionGuardInterceptor` throws on any command outside a transaction. `TransactionBehavior` (registered by `AddInfrastructure`, after `AddDispatcher`, so it runs inside logging and validation) wraps every request in one transaction, queries included: a successful command saves and commits, a failure or exception rolls back, and a query never commits. A request whose handler never touches the database implements `INoTransaction` (today only `GetCurrentUserQuery`).
- The HTTP `ITenantContext` (from the token) is the only tenant source today. A queue consumer will register its own scoped `ITenantContext` built from the message and use the same `UseTenantScopedCoreDatabase`, never a context without the interceptors.
- The app connects as `app_core` (`ConnectionStrings:core`, required at startup; no `BYPASSRLS`, not the owner). Migrations run as `core_owner` in a separate short-lived step (an AppHost resource the API waits for), never inside the API process: owner credentials can disable RLS, so no runtime process holds them. `RuntimeRoleCheck` (a hosted service from `AddInfrastructure`, started before the demo seed) refuses to start the API on a superuser, a `BYPASSRLS` role or an owner of schema `core` or of anything in it, like `check_runtime_role` in the AI service. The migrator reads only `ConnectionStrings__core-migrations`.
- The bootstrap's default privileges also cover the EF migrations history table: the first migration revokes `app_core`'s access to `core."__EFMigrationsHistory"`.
- Policies are scoped `TO app_core`, never PUBLIC, and use the tenant as a scalar subquery: `(SELECT NULLIF(current_setting('app.tenant_id', true), '')::uuid)`, evaluated once per statement. `core.tenants`: a session reads and inserts only its own row; `app_core` has no UPDATE or DELETE on it. `core.establishments`: one `FOR ALL` policy on `tenant_id`, index `(tenant_id, name)`. `core.chat_message_counts` (one row per tenant, user `sub` and UTC day; key `(tenant_id, user_id, day)`): one `FOR ALL` policy; `app_core` has SELECT, INSERT and UPDATE, no DELETE. `ChatMessageCounter` increments it with one `INSERT ... ON CONFLICT DO UPDATE ... WHERE count < limit RETURNING`, so concurrent requests never lose a count or pass the limit.
- Development only: `DemoTenantSeed` (a hosted service in Infrastructure, registered by `Program.cs` in Development and refusing to run anywhere else) creates the two demo tenants of `deploy/keycloak/README.md` at startup, plus demo establishments for each jurisdiction: "Bistro São Paulo" (BR) and "Bistro Lisboa" (EU) for Demo Bistro, "Bakery Austin" (US) for Demo Bakery. A tenant or establishment name that exists is left alone. It is idempotent and runs as `app_core` in one tenant-scoped transaction per tenant, with no owner role or bypass. Demo data is never a migration.
- Add a migration (the startup project defaults to `--project`; needs the `dotnet-ef` tool at the EF Core version, 10.0.x): `dotnet ef migrations add <Name> --project src/core/Normetry.Migrations --output-dir Schema` (or `--output-dir Data`). EF Core scaffolds tables, columns and indexes; RLS, policies, grants and revokes are hand-written `migrationBuilder.Sql(...)` in the same schema migration. EF Core refuses to apply migrations while the model has changes no migration covers.
- A state change and its outbox message are written in the same transaction. Consumers are idempotent.

## API

- Commands and queries follow the `cqrs-slice` skill. Errors are ProblemDetails. Endpoints live next to their bounded context in Api (`Establishments/EstablishmentEndpoints.cs`): `POST /establishments` (`OwnerOrManager`, 201 with `Location`), `GET /establishments` and `GET /establishments/{id}` (`Tenant`; another tenant's id is a 404, because RLS hides the row).
- JSON enums travel by name (`"Restaurant"`, `"US"`); numbers are rejected. A body that does not bind is a 400 in every environment (`ThrowOnBadRequest = false`).
- Long-running work returns `202 Accepted`; progress goes out through SignalR.
- YARP (`Normetry.Api/Gateway/AiGateway.cs`) forwards `/ai/{**catch-all}` and `/ai/establishments/{**rest}` to the AI service under the `Tenant` policy, through Aspire service discovery (`http://ai`; the AppHost passes `services__ai__http__0`). It strips every client-sent `X-Normetry-*` header (underscore spellings too) plus `Authorization`, `Cookie` and an `access_token` query parameter, then sets the internal token, tenant and user from the validated JWT, and removes `X-Normetry-*` headers from responses. Contract and rules for both sides: `src/shared/contracts/internal-http.md`. `Ai:InternalToken` (32+ characters) and `Services:ai:http:0` are required at startup; `ApiFactory` sets test values. Gateway tests (`Normetry.IntegrationTests/Gateway`) run a stub upstream on a loopback port and point `Services:ai:http:0` at it; `ChatGatewayTests` also use the test database and a fixed `TimeProvider`.
- Establishment routes (`Gateway/EstablishmentScope.cs`, a step in the custom proxy pipeline, which also keeps YARP's default steps): the core loads the establishment with `GetEstablishmentQuery` (RLS), answers 404 for a malformed (not lower-case 8-4-4-4-12), unknown or other tenant's id without forwarding, and otherwise sets `X-Normetry-Establishment-Id` and `X-Normetry-Jurisdiction`. Conversation routes without an establishment go through the catch-all and get neither header.
- Daily chat quota: `POST /ai/establishments/{id}/conversations/{conversationId}/messages` runs `CountChatMessageCommand`, committed before forwarding (a failed upstream still counts). Over the limit: 429 ProblemDetails (`chat.quota_exceeded`, `ErrorType.RateLimited`) with `Retry-After` to the next UTC midnight, nothing forwarded. Counted responses get `RateLimit-Limit`, `RateLimit-Remaining` and `RateLimit-Reset` in `Response.OnStarting` (never buffered, and they replace upstream values); unlimited plans get none. `GET /chat/quota` (`Tenant`) returns `{ limit, remaining, resetsAt }`, with `limit` and `remaining` null when unlimited. The clock is the `TimeProvider` singleton.
- Rate limiting and the per-tenant token budget live here, not in Python.

## Authentication and authorization

- JWT bearer against the Keycloak realm, with the plain `Microsoft.AspNetCore.Authentication.JwtBearer` package; setup in `Normetry.Api/Auth/AuthSetup.cs`. `Authentication:Schemes:Bearer` in `appsettings.json` holds `Authority` (`http://localhost:8180/realms/normetry`) and `ValidAudiences` (`normetry-api`). Override them per environment with `Authentication__Schemes__Bearer__Authority` and `Authentication__Schemes__Bearer__ValidAudiences__0`. The issuer and signing keys come from the authority's metadata.
- Settings honor only `Authority` and `ValidAudiences`. The binder for `Authentication:Schemes:Bearer` also reads `ValidIssuer(s)`, `SigningKeys`, `MetadataAddress`, `Forward*` and the validation flags, so `AuthSetup` replaces or clears all of them after it runs. The issuer and signing keys come only from the authority's metadata. Issuer, audience, lifetime, expiry and signature checks are always on. `RequireHttpsMetadata` is false only in Development.
- In Development the API refuses to start unless the authority is a loopback address: Development accepts `normetry-dev` tokens and plain-http metadata, so it must never run against a deployed identity provider.
- Claims keep their JWT names (`MapInboundClaims = false`). Users are identified by `sub`, never by email. `OnTokenValidated` maps `realm_access.roles` to role claims, keeping only `Owner`, `Manager` and `Auditor`. Only listed clients (`azp`) are accepted: `normetry-web` everywhere and `normetry-dev` in Development only. Any other client, or a token without `azp`, gets 401. The list is a constant in `AuthSetup.cs`, not a setting.
- Policies (`Policies` in `AuthSetup.cs`): the default policy needs an authenticated user with a `sub`. `Tenant` adds exactly one `tenant_id` claim holding a non-empty UUID in 8-4-4-4-12 form. `Owner`, `Manager` and `Auditor` each add their role on top of `Tenant`, and `OwnerOrManager` accepts either of the two. Roles have no hierarchy (an Owner is not implicitly a Manager), so an endpoint open to several roles uses a combined policy; introducing a hierarchy needs an ADR. Every tenant-scoped endpoint requires `Tenant` or a role policy, so a token without a valid tenant gets 403 before any handler runs. The fallback policy is `Tenant` too, so an endpoint that declares nothing is never anonymous. Anonymous endpoints say so with `.AllowAnonymous()` (today only `/health` and `/alive` in ServiceDefaults) and must be added to the allow-list in `AuthConfigurationTests`, which checks every mapped endpoint.
- Handlers read the caller through `ICurrentUser` (user id, roles) and `ITenantContext` (tenant id) in `Normetry.Application/Abstractions`. `HttpCurrentUser` (Api) implements both from the validated principal only: the tenant never comes from the body, query string or headers. Reading `TenantId` without a valid tenant throws, which means the endpoint is missing its policy.

## Tests

Test projects live in `src/core/tests/`: xUnit v3 on Microsoft.Testing.Platform (selected in the root `global.json`). A test project needs at least one test, because the platform fails a run with zero tests.

- Domain and BuildingBlocks: unit tests (`Normetry.UnitTests`; it references Api for the ProblemDetails mapping).
- Endpoints and auth: `Normetry.IntegrationTests` runs the API in memory with `WebApplicationFactory<Program>` (`ApiFactory`). The factory replaces the authority's metadata with a static configuration that trusts a test issuer and an RSA key generated per run, and `ApiFactory.CreateToken` builds Keycloak-shaped access tokens, so no Keycloak is needed. For environment-specific behavior use `factory.WithWebHostBuilder(b => b.UseEnvironment("Production"))`.
- Handlers and persistence: `Normetry.IntegrationTests/Database`. `DatabaseFixture` (the `database` collection) starts one `pgvector/pgvector:0.8.7-pg17` container per run with the real bootstrap from `deploy/postgres/init/` (copied next to the tests) and random passwords, then runs `CoreMigrator` as `core_owner`. Assertions connect as the real roles, never as the superuser: `Session` opens a transaction as a role with an optional tenant set the way the interceptor does it. `RowLevelSecurityTests` holds the `rls-table` isolation tests, `CatalogTests` the catalog checks (RLS enabled and forced on every table `app_core` can use, policies only `TO app_core`, exact grants, no access to the history) `TenantTransactionTests` the interceptor, the guard and the seed, and `RuntimeRoleCheckTests` the startup role check. A new tenant-owned table adds its cases there. Endpoint tests that need data use `fixture.Api`, an `ApiFactory` connected as `app_core`; its Development seed creates the demo tenants `ApiFactory.TenantA` and `TenantB`. Without a database, `ApiFactory` gets an address it never connects to and drops the role check and the seed.
- Docker missing: the fixture records the reason and every database test is skipped (the test class constructor calls `SkipWithoutDocker()`), except when `CI` is set, where they fail. Same rule as the Python tests.
- Architecture: NetArchTest rules (`Normetry.ArchitectureTests`).

## Commands

From the repo root:

- `dotnet build` · `dotnet test`
- `dotnet run --project src/core/Normetry.AppHost` (needs Docker): Aspire dashboard at `https://localhost:17081`, login link in the console. Trust the HTTPS dev certificate once with `dotnet dev-certs https --trust`, otherwise the services cannot export telemetry to the dashboard (TLS verify fails). If `mcr.microsoft.com` is unreachable, set `ASPIRE_ENABLE_CONTAINER_TUNNEL=false`: the default container tunnel image is built from it.
- `dotnet tool restore` then `dotnet csharpier check .` (or `format .`)

## Configuration

- Secrets through `dotnet user-secrets`, Aspire parameters or environment variables. `appsettings*.json` holds no secrets.
- Chat plans (`Chat` in `appsettings.json`, bound to `ChatOptions` and validated by `AddChat` at startup): `Chat:Plans:{plan}:DailyMessagesPerUser` (unset or null means no limit; defaults `demo` 20, `standard` 200, `unlimited` none), `Chat:DefaultPlan` (`demo`) and `Chat:TenantPlans:{tenantId}` = plan name. The API refuses to start on an unknown plan name, a tenant key that is not a UUID or a limit below 1. A change is a configuration change and a restart.
- The AppHost generates every secret parameter on the first run (`internal-token`, the five role passwords, the Postgres and Keycloak admin passwords) and keeps it in its user secrets. It passes the API `ConnectionStrings__core` (`app_core`), `Ai__InternalToken` and the Keycloak reference (the API's JWT authority comes from `appsettings.json` instead, because the token issuer is the fixed `http://localhost:8180` URL); the AI service gets `NORMETRY_INTERNAL_TOKEN` and `NORMETRY_DATABASE_URL` (`app_ai`). Owner credentials go only to the migration steps: `core-migrate` (the Migrations project) gets nothing but `ConnectionStrings__core-migrations` (`core_owner`), and the API waits for it to complete; `ai-migrate` gets `NORMETRY_MIGRATIONS_DATABASE_URL` (`ai_owner`). Roles and schemas: `deploy/postgres/README.md`; realm, tenants and demo users: `deploy/keycloak/README.md`.
- The AI service answers 401 on every route without `X-Normetry-Internal-Token`, so its health check is a custom one in `AppHost.cs` that sends the token, not `WithHttpHealthCheck`.
- Formatter: CSharpier as a local dotnet tool (`.config/dotnet-tools.json`); the hook runs it on every edited `.cs` file.
