# src/core — .NET 10 core

## Projects

Solution: `Normetry.slnx` at the repo root. Shared build settings live in the root `Directory.Build.props` (net10.0, nullable, warnings as errors) and package versions in `Directory.Packages.props` (central package management: `PackageReference` items carry no `Version`).

- `Normetry.BuildingBlocks` — shared primitives with no Normetry, EF Core or ASP.NET Core dependency. `Cqrs/` holds the in-house dispatcher (ADR 009): commands, queries, handlers, `IDispatcher`, pipeline behaviors (logging, FluentValidation) and `AddDispatcher(...)`, which scans for handlers and validators. `Results/` holds `Result`, `Result<T>` and `Error` for expected failures; `Normetry.Api` maps a failed result to ProblemDetails with `ToProblemDetails()`.
- `Normetry.Domain` — entities, value objects, domain events. References only BuildingBlocks: no EF Core, ASP.NET Core or dispatcher.
- `Normetry.Application` — commands, queries, handlers and validators, one folder per bounded context. References Domain and BuildingBlocks.
- `Normetry.Infrastructure` — EF Core (Npgsql), outbox, messaging, blob storage; implements Application abstractions. References Application.
- `Normetry.Migrations` — EF Core migrations only, in `Schema/` (structure, RLS, grants) and `Data/` (rows every environment needs; rules in `Data/README.md`), one history. A short-lived console app (`CoreMigrator`) the AppHost runs as `core_owner` before the API starts; see "Database migrations" in the root `CLAUDE.md`. References Infrastructure; nothing references it except the AppHost and the tests.
- `Normetry.Api` — composition root: endpoints, OIDC/JWT auth, YARP `/ai/*`, SignalR hubs, rate limiting. References Application, Infrastructure and ServiceDefaults.
- `Normetry.ServiceDefaults` — Aspire service defaults: OpenTelemetry, health checks (`/health`, `/alive`, Development only), service discovery, HTTP resilience.
- `Normetry.AppHost` — Aspire orchestration of every service and container. DCP and the dashboard come from NuGet (`AspireUseCliBundle=false`), so no Aspire CLI install is needed.

Layer dependencies are enforced by NetArchTest (`tests/Normetry.ArchitectureTests`). When a rule fails, fix the dependency, not the rule. A reference pointing up the layers (for example Domain → Infrastructure) is already rejected by MSBuild as a circular reference; the tests catch leaks such as EF Core or ASP.NET Core types in Domain.

Bounded contexts: Tenancy & Identity, Establishments, Documents, Regulations (read-only here), Assessments, Usage & Budget, Notifications.

## Persistence

- Schema `core` only, through EF Core migrations. Never touch `ai.*`.
- `CoreDbContext` (`Normetry.Infrastructure/Persistence`) uses Npgsql with EFCore.NamingConventions, so every table, column, key and index name is lower-case snake_case (`core.establishments.tenant_id`, `pk_establishments`). The history table keeps its name, `core."__EFMigrationsHistory"`, but its columns are snake_case too (`migration_id`, `product_version`).
- Tenant-owned tables follow the `rls-table` skill. Handlers never set the tenant and never filter by it: they go through repositories (interfaces in Application, EF Core in Infrastructure) and RLS returns only the current tenant's rows.
- No SQL reaches tenant data without a tenant (fail closed). Every runtime context is built with `UseTenantScopedCoreDatabase(connectionString, ITenantContext)`; `UseCoreDatabase`, which has no interceptors, is internal and visible only to `Normetry.Migrations`. The tenant-scoped builder adds two interceptors: `TenantTransactionInterceptor` runs `set_config('app.tenant_id', <tenant>, true)` as the first statement of every transaction EF Core starts or adopts (and throws when that transaction or session already holds another tenant), and `TransactionGuardInterceptor` throws on any command outside a transaction. `TransactionBehavior` (registered by `AddInfrastructure`, after `AddDispatcher`, so it runs inside logging and validation) wraps every request in one transaction, queries included: a successful command saves and commits, a failure or exception rolls back, and a query never commits.
- Two tenant sources, nothing else: a request's comes from its token (`HttpCurrentUser`), and a background scope's from `BackgroundTenant` (Infrastructure), which the outbox dispatcher sets from the outbox row, the status consumer from the message envelope's `tenantId` (never from AMQP properties or headers) and the timeout sweeper from the tenant it visits. `Set` is internal to Infrastructure and runs once, before the scope resolves `ITenantContext` (a later one throws); `AuthSetup` resolves `ITenantContext` to it when set, otherwise to the token's. The scope's database is the same `UseTenantScopedCoreDatabase`, never a context without the interceptors. The user works the same way: a request's comes from its token, and only the development document seed sets `BackgroundUser` (Infrastructure, `Set` internal, once, before the scope resolves `ICurrentUser`), which `AuthSetup` then resolves `ICurrentUser` to.
- The app connects as `app_core` (`ConnectionStrings:core`, required at startup; no `BYPASSRLS`, not the owner). Migrations run as `core_owner` in a separate short-lived step (an AppHost resource the API waits for), never inside the API process: owner credentials can disable RLS, so no runtime process holds them. The one query without a tenant, the tenant list of the outbox dispatcher and the timeout sweeper (`OutboxTenantList`), connects as `core_dispatcher` (`ConnectionStrings:core-dispatcher`, read when those services start), whose only table privilege is SELECT on `core.outbox_tenants` (ADR 003 amendment); nothing else uses that connection string. `RuntimeRoleCheck` (a hosted service from `AddInfrastructure`, started before the demo seed) refuses to start the API when either connection string is a superuser, a `BYPASSRLS` role or an owner of schema `core` or of anything in it, like `check_runtime_role` in the AI service. The migrator reads only `ConnectionStrings__core-migrations`.
- The bootstrap's default privileges also cover the EF migrations history table: the first migration revokes `app_core`'s access to `core."__EFMigrationsHistory"`.
- Policies are scoped `TO app_core` (the tenant list's read `TO core_dispatcher`), never PUBLIC, and use the tenant as a scalar subquery: `(SELECT NULLIF(current_setting('app.tenant_id', true), '')::uuid)`, evaluated once per statement. `core.tenants`: a session reads and inserts only its own row; `app_core` has no UPDATE or DELETE on it. `core.establishments`: one `FOR ALL` policy on `tenant_id`, index `(tenant_id, name)`. `core.chat_message_counts` (one row per tenant, user `sub` and UTC day; key `(tenant_id, user_id, day)`): one `FOR ALL` policy; `app_core` has SELECT, INSERT and UPDATE, no DELETE. `ChatMessageCounter` increments it with one `INSERT ... ON CONFLICT DO UPDATE ... WHERE count < limit RETURNING`, so concurrent requests never lose a count or pass the limit.
- Users, profiles and permissions (Tenancy & Identity, `Normetry.Domain/Identity`): `core.permissions` is the global catalog (no tenant, no RLS, the one exception in `CatalogTests`), filled by the `InsertPermissionCatalog` data migration with the names in `Permissions`; `app_core` only reads it. `core.profiles` (key `(tenant_id, id)`, unique `(tenant_id, name)`), `core.profile_permissions`, `core.users` (key `(tenant_id, id)`, unique `(tenant_id, sub)`; display name and email from the token, for display only) and `core.user_profiles` are tenant-owned, one `FOR ALL` policy each. The links reference `(tenant_id, id)`, so a link can never join rows of two tenants even with a known id. `app_core` has no UPDATE on the links and no DELETE on users. System profiles carry a `system_key` (`owner`, `manager`, `auditor`; unique per tenant) and are created at runtime with the tenant, never by a migration (RLS keeps `core_owner` out): Owner has `grants_all` (every catalog permission, present and future, with no rows; a check ties it to `system_key = 'owner'`), Manager every permission but `profiles.manage`, Auditor `establishments.read`, `documents.read`, `chat.ask`, `inspections.read`, `profiles.read` (`Profile.DefaultPermissions`). A user row is created on first sign-in (`SyncCurrentUserCommand`, one `INSERT ... ON CONFLICT`, skipped when the core has no row for the tenant) and its name and email follow the token.
- Development only: `DemoTenantSeed` (a hosted service in Infrastructure, registered by `Program.cs` in Development and refusing to run anywhere else) creates the two demo tenants of `deploy/keycloak/README.md` at startup, each with its three system profiles, its demo users (by their fixed Keycloak ids) and their profiles (`bistro.owner` and `bakery.owner` Owner, `bistro.manager` Manager, `bakery.auditor` Auditor), plus demo establishments for each jurisdiction: "Bistro São Paulo" (BR) and "Bistro Lisboa" (EU) for Demo Bistro, "Bakery Austin" (US) for Demo Bakery. For a tenant that exists it is also the startup step that adds the system profiles it lacks, and gives a system profile that holds no `inspections.*` permission its defaults of them (so a later change in Settings survives a restart); `app_core` cannot list tenants under RLS, so it covers only the tenants it knows. A tenant, system profile, user (by `sub`) or establishment name that exists is left alone. It is idempotent and runs as `app_core` in one tenant-scoped transaction per tenant, with no owner role or bypass. Demo data is never a migration.
- Development only: `DemoDocumentSeed` (a `BackgroundService` in Infrastructure, registered by `Program.cs` in Development; `StartAsync` throws anywhere else) waits for `ApplicationStarted`, then reads every `manifest.json` under `DemoDocuments:Directory` (default: `evals/establishments` from the API's content root; see its README) and uploads each listed file with `UploadDocumentCommand`, or `UploadDocumentVersionCommand` when the file changed, in its own scope with `BackgroundTenant` set to the establishment's tenant and `BackgroundUser` to its demo Owner. A document (matched by title, not deleted) whose current or newest version has the file's SHA-256 is skipped. An entry's optional `expiresOn` is passed to the upload, and a document whose date differs from the manifest's (none when absent) gets it through `SetDocumentExpiryCommand`, without a new version. Failures are logged and never stop the API.
- Add a migration (the startup project defaults to `--project`; needs the `dotnet-ef` tool at the EF Core version, 10.0.x): `dotnet ef migrations add <Name> --project src/core/Normetry.Migrations --output-dir Schema` (or `--output-dir Data`). EF Core scaffolds tables, columns and indexes; RLS, policies, grants and revokes are hand-written `migrationBuilder.Sql(...)` in the same schema migration. EF Core refuses to apply migrations while the model has changes no migration covers.
- Messaging (ADR 005, contracts in `src/shared/contracts/messages`): `IOutbox.EnqueueAsync` adds a `core.outbox_messages` row (key `(tenant_id, id)`, the id is the envelope's `messageId`, the body is the whole envelope as `json`, plus the writing request's `traceparent`) to the request's unit of work, so `TransactionBehavior` saves it with the state change, and records the tenant in `core.outbox_tenants`. `OutboxDispatcher` (hosted) publishes a tenant as soon as a command of this process commits its messages (`Outbox` adds an `AfterCommit` action that signals `OutboxSignal`), and every 30 seconds visits each tenant of `core.outbox_tenants` for the rest (another instance, a crash, a broker that was down). Each tenant runs in its own scope and transaction, locks up to 50 pending rows `FOR UPDATE SKIP LOCKED`, publishes them to `normetry.events` with publisher confirms and `mandatory` (an unroutable or nacked message stays pending and stops the tenant's batch, keeping order) and sets `sent_at` only after the confirm: at least once. `core.outbox_tenants` holds only tenant ids; its policies are the one cross-tenant read (`SELECT USING (true)` `TO core_dispatcher`, the role's only table privilege) and an `INSERT` `TO app_core` for the session's own tenant only. app_core has INSERT and nothing else on it, so no request path can read the list (`Outbox` writes with `ON CONFLICT DO NOTHING`, which needs no SELECT). `core.inbox_messages` (key `(tenant_id, message_id)`) records each consumed message in the transaction that applies it (`IInbox`, one `INSERT ... ON CONFLICT DO NOTHING`), so a redelivery changes nothing. app_core has no DELETE on any of them and no UPDATE on the inbox or the tenant list. Rows are kept (no retention yet). `MessageJson` writes and reads the envelope (camelCase only, case-sensitive); a body off the contract is a `MessageFormatException`. The dispatcher and the sweeper share `OutboxTenantList.ForEachAsync` and `TenantScope`: a tenant's failure is logged and the next tenant goes on.
- Documents (`Normetry.Domain/Documents`): `core.documents` (key `(tenant_id, id)`, soft delete with `deleted_at`, references its establishment by `(tenant_id, id)`, so the establishments table has the alternate key `ak_establishments_tenant_id_id`) and `core.document_versions` (key `(tenant_id, id)`, unique `(tenant_id, document_id, number)`, the uploader by `(tenant_id, uploaded_by)` → `core.users`, a partial index for `Processing` versions). One `FOR ALL` policy each, no DELETE. Status runs `Uploaded → Processing → Indexed | Failed`; every transition returns whether it changed anything, so a late or repeated event is a no-op. Indexed is accepted from any other status (after a timeout too); Failed only from Uploaded or Processing. The current version is the newest Indexed one, and only one version is in flight (Uploaded or Processing) at a time. Uploads, deletes and status events lock the document row first; an upload locks the establishment row before counting its documents. `expires_on` (`date`, nullable) is the optional last valid day (a license, a certificate); any date is accepted, a past one too, and a deleted document keeps its date. The blob path is `tenants/{tenant}/establishments/{establishment}/documents/{document}/versions/{version}/file{ext}` (lower-case ids; the last segment is fixed, so no client text reaches the path, logs or traces); the uploaded name is kept in `file_name` for display.
- Inspections (`Normetry.Domain/Inspections`, migration `CreateInspections`): `core.inspections` (key `(tenant_id, id)`, the establishment by `(tenant_id, establishment_id)`, `requested_by` the requester's `sub`, `themes` `jsonb`, index `(tenant_id, establishment_id, requested_at)` for the list, and the partial unique index `ix_inspections_tenant_id_establishment_id` on `(tenant_id, establishment_id)` where status is `Requested` or `Running`), `core.findings` (key `(tenant_id, id)`, the inspection by `(tenant_id, inspection_id)` with cascade, citations and `original` as `jsonb`, `reviewed_by` → `core.users` by `(tenant_id, id)`), `core.action_items` (one per finding, unique `(tenant_id, finding_id)`, `updated_by` → `core.users`) and `core.inspection_counts` (key `(tenant_id, day)`, the daily start count, like the chat counter). One `FOR ALL` policy each, no DELETE. Status runs `Requested → Running → Completed | Failed`; every transition returns whether it changed anything; a completion is accepted from any other status (a late one after `timed_out` too); progress replaces the snapshot only with more items evaluated. Review: accept, reject (note required, ≤ 1000), edit (rationale ≤ 2000, action ≤ 1000; the first edit keeps `original`; action text and due date together create a missing action item); the latest decision wins. Severity, verdict, confidence and theme are the contract's snake_case codes (`Finding.Severities`, `Finding.Verdicts`, `Finding.Confidences`, `ThemeProgress.Themes`, also what `MessageJson` checks); the JSON columns are EF Core complex types (`ComplexCollection(...).ToJson()` over the private lists) and the message payloads reuse those domain records.

## API

- Commands and queries follow the `cqrs-slice` skill. Errors are ProblemDetails. Endpoints are MVC controllers (`[ApiController]`, mapped by `MapControllers`) next to their bounded context in Api (`Establishments/EstablishmentsController.cs`); an action dispatches and maps a failure with `result.ToActionResult()`. Only health, YARP and SignalR are mapped directly. `POST /establishments` (`establishments.manage`, 201 with `Location`), `GET /establishments` and `GET /establishments/{id}` (`establishments.read`; another tenant's id is a 404, because RLS hides the row). `GET /me` (`Tenant` only) first syncs the caller's user row (first sign-in), then returns `{ userId, tenantId, tenantName, permissions, profiles }`: the tenant name comes from the caller's own `core.tenants` row (null when the core has none), `profiles` are `{ id, name, systemKey }` and `permissions` what they grant.
- Profile and user management (`Identity/ProfilesController.cs`, `UsersController.cs`, `PermissionsController.cs`): `GET /permissions` (catalog `[{ name }]`), `GET /profiles` (`[{ id, name, systemKey, grantsAll, permissionCount }]`, the whole catalog counted for Owner), `GET /profiles/{id}` (`{ id, name, systemKey, grantsAll, permissions }`) and `GET /users` (`[{ id, displayName, email, isCurrentUser, profiles: [{ id, name, systemKey }] }]`) need `profiles.read`; `POST /profiles` (`{ name }`, 201 with `Location`), `PATCH /profiles/{id}` (`{ name }`, 204), `DELETE /profiles/{id}` (204; the database takes it from its users), `PUT /profiles/{id}/permissions` (`{ permissions }`, 200 with the profile as stored: each area's `.read` is added when another permission of the area is given) and `PUT`/`DELETE /users/{userId}/profiles/{profileId}` (204, idempotent) need `profiles.manage`. Refusals (`IdentityErrors`): `profile.not_found` and `user.not_found` (404, also for another tenant's ids), `profile.name_taken` (409, exact name in the tenant), `profile.system_profile` (409, renaming or deleting Owner, Manager or Auditor), `profile.owner_locked` (409, changing Owner's permissions) and `profile.last_owner` (409, the lockout guard). Owner changes and permission saves lock the profile row first (`SELECT ... FOR UPDATE`), so two Owners removing each other cannot both succeed. `profiles.manage` is as strong as Owner: it can assign Owner.
- JSON enums travel by name (`"Restaurant"`, `"US"`); numbers are rejected (MVC JSON options). A body that does not bind is a 400 from `[ApiController]`. FluentValidation is the only input validator: MVC's implicit `[Required]` on non-nullable strings is off, so an invalid field always gets the `validation` problem with its field errors.
- Documents (`Documents/DocumentsController.cs`): `POST /establishments/{id}/documents` (multipart `file`, `title`, `type` = `Sop`, `License`, `Log`, `Report` or `Other`, and an optional `expiresOn` as `YYYY-MM-DD`; an empty value means none, anything else not an ISO date is the `validation` problem on `ExpiresOn`) and `POST /documents/{id}/versions` (multipart `file`) need `documents.upload` and answer 202 with `Location: /documents/{id}` and the document; `PATCH /establishments/{establishmentId}/documents/{documentId}` (`documents.upload`, JSON `{ "expiresOn": "YYYY-MM-DD" | null }`, the field required, so `{}` is a 400) sets or clears the expiry date and answers 204 (`SetDocumentExpiryCommand`; another tenant's, another establishment's or a deleted document is `document.not_found`; nothing is announced to the AI service). `GET /establishments/{id}/documents` (`[{ id, establishmentId, title, type, expiresOn, createdAt, updatedAt, currentVersionNumber, latestVersion }]`, most recently updated first; optional `expired=true` keeps `expiresOn` before today, `expiringWithinDays=N` (1 to 365) keeps today ≤ `expiresOn` ≤ today + N, today in UTC from the `TimeProvider`; both at once, or N out of range, is the `validation` problem) and `GET /documents/{id}` (`{ id, establishmentId, title, type, expiresOn, createdAt, updatedAt, currentVersionNumber, versions }`, newest first) need `documents.read`; `DELETE /documents/{id}` (`documents.delete`) soft-deletes, answers 204 and enqueues `DocumentDeleted`. A version is `{ id, number, fileName, contentType, size, status, failureCode, failureReason, uploadedBy: { id, displayName }, uploadedAt, statusChangedAt, chunkCount, pageCount, language }`; `failureCode` is a contract reason code or `timed_out`. An upload checks the file (`DocumentFiles`: PDF, DOCX, TXT or CSV by extension, content type and first bytes, a DOCX must hold `word/document.xml`, at most 10 MiB; `.csv` also accepts `application/vnd.ms-excel`, which Windows browsers send), locks and counts, stores the blob (`IDocumentBlobStore`), then the version (Uploaded) and `DocumentUploaded` commit together. Refusals (`DocumentErrors`): `document.unsupported_format`, `document.invalid_content`, `document.empty`, `document.too_large` (400), `document.not_found`, `establishment.not_found` (404), `document.version_in_flight`, `document.limit_reached` (`Documents:MaxDocumentsPerEstablishment`, 50) and `document.version_limit_reached` (`Documents:MaxVersionsPerDocument`, 20) (409).
- Ingestion status (`Messaging/DocumentStatusConsumer.cs`): the hosted consumer declares `core.document-status` and its dead-letter queue as the contract says, takes one message at a time and hands each body to `DocumentStatusMessages`, which opens a scope with the envelope's tenant and dispatches `RecordIngestionCommand` (inbox, then the transition). An error while the database does not answer (`SELECT 1` as app_core) holds the message unacknowledged and handles it again every 10 seconds; other errors are retried after 2, 10, 30, then 60 seconds by a reject with requeue (the broker counts it; `x-delivery-limit: 4` dead-letters the fifth); a body off the contract, or a core → ai message, is dead-lettered at once. `ProcessingTimeoutSweeper` (hosted, every 30 seconds, independent of the broker) runs `TimeOutProcessingCommand` per tenant of `core.outbox_tenants`: a version Processing for longer than `Documents:ProcessingTimeout` fails with `timed_out`.
- Live status (`Documents/DocumentsHub.cs`): the SignalR hub at `/hubs/documents` is WebSockets only, closes when the token expires and needs `documents.read` to connect (`[HasPermission]` on the class) and on each method (its own attribute; SignalR checks only method attributes per call). `JoinEstablishment(establishmentId)` loads the establishment under the caller's tenant (RLS; another tenant's id fails with a `HubException` `establishment.not_found`) and moves the connection to the group `tenants/{tenant}/establishments/{establishment}`. After their transaction commits, the consumer and the sweeper push `DocumentStatusChanged` with `{ establishmentId, documentId, versionId, versionNumber, status, failureCode, failureReason, currentVersionNumber, changedAt }` (enums by name) to that group. No backplane yet: a push reaches the clients of the instance that applied the change.
- Long-running work returns `202 Accepted`; progress goes out through SignalR.
- YARP (`Normetry.Api/Gateway/AiGateway.cs`) forwards `/ai/{**catch-all}` and `/ai/establishments/{**rest}` to the AI service under the `chat.ask` permission policy (which includes `Tenant`), through Aspire service discovery (`http://ai`; the AppHost passes `services__ai__http__0`). It strips every client-sent `X-Normetry-*` header (underscore spellings too) plus `Authorization`, `Cookie` and an `access_token` query parameter, then sets the internal token, tenant and user from the validated JWT, and removes `X-Normetry-*` headers from responses. Contract and rules for both sides: `src/shared/contracts/internal-http.md`. `Ai:InternalToken` (32+ characters) and `Services:ai:http:0` are required at startup; `ApiFactory` sets test values. Gateway tests (`Normetry.IntegrationTests/Gateway`) run a stub upstream on a loopback port and point `Services:ai:http:0` at it; `ChatGatewayTests` also use the test database and a fixed `TimeProvider`.
- Establishment routes (`Gateway/EstablishmentScope.cs`, a step in the custom proxy pipeline, which also keeps YARP's default steps): the core loads the establishment with `GetEstablishmentQuery` (RLS), answers 404 for a malformed (not lower-case 8-4-4-4-12), unknown or other tenant's id without forwarding, and otherwise sets `X-Normetry-Establishment-Id` and `X-Normetry-Jurisdiction`. Conversation routes without an establishment go through the catch-all and get neither header.
- Daily chat quota: `POST /ai/establishments/{id}/conversations/{conversationId}/messages` runs `CountChatMessageCommand`, committed before forwarding (a failed upstream still counts). Over the limit: 429 ProblemDetails (`chat.quota_exceeded`, `ErrorType.RateLimited`) with `Retry-After` to the next UTC midnight, nothing forwarded. Counted responses get `RateLimit-Limit`, `RateLimit-Remaining` and `RateLimit-Reset` in `Response.OnStarting` (never buffered, and they replace upstream values); unlimited plans get none. `GET /chat/quota` (`chat.ask`) returns `{ limit, remaining, resetsAt }`, with `limit` and `remaining` null when unlimited. The clock is the `TimeProvider` singleton.
- Rate limiting and the per-tenant token budget live here, not in Python.

## Authentication and authorization

- JWT bearer against the Keycloak realm, with the plain `Microsoft.AspNetCore.Authentication.JwtBearer` package; setup in `Normetry.Api/Auth/AuthSetup.cs`. `Authentication:Schemes:Bearer` in `appsettings.json` holds `Authority` (`http://localhost:8180/realms/normetry`) and `ValidAudiences` (`normetry-api`). Override them per environment with `Authentication__Schemes__Bearer__Authority` and `Authentication__Schemes__Bearer__ValidAudiences__0`. The issuer and signing keys come from the authority's metadata.
- Settings honor only `Authority` and `ValidAudiences`. The binder for `Authentication:Schemes:Bearer` also reads `ValidIssuer(s)`, `SigningKeys`, `MetadataAddress`, `Forward*` and the validation flags, so `AuthSetup` replaces or clears all of them after it runs. The issuer and signing keys come only from the authority's metadata. Issuer, audience, lifetime, expiry and signature checks are always on. `RequireHttpsMetadata` is false only in Development.
- In Development the API refuses to start unless the authority is a loopback address: Development accepts `normetry-dev` tokens and plain-http metadata, so it must never run against a deployed identity provider.
- On paths under `/hubs` only, the token may come in the `access_token` query parameter (browsers cannot set headers on a WebSocket); everywhere else a query token is ignored.
- Claims keep their JWT names (`MapInboundClaims = false`). Users are identified by `sub`, never by email. Realm roles authorize nothing and are not mapped; the realm defines none. Only listed clients (`azp`) are accepted: `normetry-web` everywhere and `normetry-dev` in Development only. Any other client, or a token without `azp`, gets 401. The list is a constant in `AuthSetup.cs`, not a setting.
- Policies (`Policies` in `AuthSetup.cs`): the default policy needs an authenticated user with a `sub`. `Tenant` adds exactly one `tenant_id` claim holding a non-empty UUID in 8-4-4-4-12 form. Every tenant-scoped endpoint requires `Tenant` directly (only `/me`) or through a permission policy, so a token without a valid tenant gets a plain 403 before any handler runs. The fallback policy is `Tenant` too, so an endpoint that declares nothing is never anonymous. Anonymous endpoints say so with `.AllowAnonymous()` (today only `/health` and `/alive` in ServiceDefaults) and must be added to the allow-list in `AuthConfigurationTests`, which checks every mapped endpoint.
- Permissions (ADR 012, `Auth/HasPermissionAttribute.cs` and `Auth/PermissionAuthorization.cs`): every controller action carries `[HasPermission(Permissions.Area.Action)]` (names in `Normetry.Domain/Identity/Permissions.cs`) or `[AllowAnonymous]`; `AuthConfigurationTests` reflects over every action and fails on one with neither (the one listed exception is `MeController.Get`) or with a name outside the catalog. `PermissionPolicyProvider` turns `permission:{name}` into `Tenant` plus a `PermissionRequirement` (an unknown name throws); `PermissionHandler` loads the caller's permissions once per authorization with `GetCurrentUserPermissionsQuery` (the tenant transaction and RLS, no cache) and never writes: `/me` creates the user row. A caller with a valid tenant who lacks the permission gets a 403 problem with the code `permission.denied` (`PermissionDeniedResultHandler`); a user with no profile gets it everywhere but `/me`. YARP routes take the same policy names (`HasPermissionAttribute.PolicyName`). `PermissionTests` covers each action with a user lacking only its permission and one holding only it; a new action adds its row there.
- Handlers read the caller through `ICurrentUser` (user id, display name and email, the last two for display only) and `ITenantContext` (tenant id) in `Normetry.Application/Abstractions`. `HttpCurrentUser` (Api) implements both from the validated principal only: the tenant never comes from the body, query string or headers. Background scopes use `BackgroundTenant` and, for the development document seed only, `BackgroundUser` instead. Reading `TenantId` without a valid tenant throws, which means the endpoint is missing its policy.

## Tests

Test projects live in `src/core/tests/`: xUnit v3 on Microsoft.Testing.Platform (selected in the root `global.json`). A test project needs at least one test, because the platform fails a run with zero tests.

- Domain and BuildingBlocks: unit tests (`Normetry.UnitTests`; it references Api for the ProblemDetails mapping).
- Endpoints and auth: `Normetry.IntegrationTests` runs the API in memory with `WebApplicationFactory<Program>` (`ApiFactory`). The factory replaces the authority's metadata with a static configuration that trusts a test issuer and an RSA key generated per run, and `ApiFactory.CreateToken` builds Keycloak-shaped access tokens, so no Keycloak is needed. For environment-specific behavior use `factory.WithWebHostBuilder(b => b.UseEnvironment("Production"))`.
- Handlers and persistence: `Normetry.IntegrationTests/Database`. `DatabaseFixture` (the `database` collection) starts one `pgvector/pgvector:0.8.7-pg17` container per run with the real bootstrap from `deploy/postgres/init/` (copied next to the tests) and random passwords, then runs `CoreMigrator` as `core_owner`. Assertions connect as the real roles, never as the superuser: `Session` opens a transaction as a role with an optional tenant set the way the interceptor does it. `RowLevelSecurityTests` holds the `rls-table` isolation tests, `CatalogTests` the catalog checks (RLS enabled and forced on every table `app_core` or `core_dispatcher` can use, policies only `TO` those two, exact grants, `core_dispatcher` holding only SELECT on the tenant list, no access to the history) `TenantTransactionTests` the interceptor, the guard and the seed, and `RuntimeRoleCheckTests` the startup role check. A new tenant-owned table adds its cases there. `CatalogTests` and `RowLevelSecurityTests` also cover the messaging and document tables. Endpoint tests that need data use `fixture.Api`, an `ApiFactory` connected as `app_core` (and `core_dispatcher` through `DispatcherConnectionString`, which every `ApiFactory` with a database sets, since the role check reads it) (`AuthenticationTests` too, since `/me` reads the tenant row); its Development seed creates the demo tenants `ApiFactory.TenantA` and `TenantB` and their demo users (`ApiFactory.BistroOwner`, the default token's `sub`, and the others). `TestTenants` makes a test's own tenant, Owner and users with exact permissions in SQL. The gateway tests need the database too, since `/ai/*` loads the caller's permissions. Without a database, `ApiFactory` gets an address it never connects to and drops the role check and the seed. `ApiFactory` never runs the background messaging services (dispatcher, consumer, sweeper): tests drive them directly (`ActivatorUtilities.CreateInstance`), so no test publishes or consumes another's messages. It stores blobs in `InMemoryBlobStore` (`api.Blobs`) and points `DemoDocuments:Directory` at a folder that does not exist, so the document seed runs but uploads nothing; `DemoDocumentSeedTests` call it with their own folder and tenant, and upload the real placeholders (copied next to the tests as `demo-documents/`) into a test tenant. ## Configuration

- Secrets through `dotnet user-secrets`, Aspire parameters or environment variables. `appsettings*.json` holds no secrets.
- Documents (`Documents` in `appsettings.json`, bound to `DocumentsOptions` and validated at startup): `MaxDocumentsPerEstablishment` (50; deleted documents do not count), `ProcessingTimeout` (`00:15:00`) and `BlobContainer` (`documents`). `ConnectionStrings:rabbitmq` (an AMQP URI) and `ConnectionStrings:blobs` (the storage account) are required at startup.
- Chat plans (`Chat` in `appsettings.json`, bound to `ChatOptions` and validated by `AddChat` at startup): `Chat:Plans:{plan}:DailyMessagesPerUser` (unset or null means no limit; defaults `demo` 20, `standard` 200, `unlimited` none), `Chat:DefaultPlan` (`demo`) and `Chat:TenantPlans:{tenantId}` = plan name. The API refuses to start on an unknown plan name, a tenant key that is not a UUID or a limit below 1. A change is a configuration change and a restart.
- The AppHost generates every secret parameter on the first run (`internal-token`, the six role passwords, `rabbitmq-password`, the Postgres and Keycloak admin passwords) and keeps it in its user secrets. It also runs RabbitMQ (`rabbitmq`, `4.3-alpine`, no management plugin, a data volume and the generated `rabbitmq-password`) and Azurite (`storage` with `blobs`; the AppHost creates the `documents` container; a data volume). It passes the API `ConnectionStrings__core` (`app_core`), `ConnectionStrings__core-dispatcher` (`core_dispatcher`), `ConnectionStrings__rabbitmq`, `ConnectionStrings__blobs`, `Documents__BlobContainer`, `Ai__InternalToken` and the Keycloak reference (the API's JWT authority comes from `appsettings.json` instead, because the token issuer is the fixed `http://localhost:8180` URL); the AI service gets `NORMETRY_INTERNAL_TOKEN`, `NORMETRY_DATABASE_URL` (`app_ai`), `NORMETRY_RABBITMQ_URL` (which turns its document consumer on), `NORMETRY_BLOB_CONNECTION_STRING` and `NORMETRY_BLOB_CONTAINER=documents`. Owner credentials go only to the migration steps: `core-migrate` (the Migrations project) gets nothing but `ConnectionStrings__core-migrations` (`core_owner`), and the API waits for it to complete; `ai-migrate` gets `NORMETRY_MIGRATIONS_DATABASE_URL` (`ai_owner`). Roles and schemas: `deploy/postgres/README.md`; realm, tenants and demo users: `deploy/keycloak/README.md`.
- The web app (`web`, `AddViteApp` on `src/web`) runs `npm install` and then the Vite dev server on the fixed port 5173 (the only origin the `normetry-web` Keycloak client accepts). It gets `NORMETRY_API_URL` (the API's http endpoint, target of the dev server's `/api` proxy, so the API needs no CORS) and `VITE_OIDC_AUTHORITY`, and waits for the API.
- Keycloak, the AI service and the web app call `WithoutHttpsCertificate()`: once the HTTPS dev certificate is trusted, Aspire would otherwise serve them over https, which changes the token issuer the API expects (`http://localhost:8180/realms/normetry`), hands the API `services__ai__https__0` instead of `services__ai__http__0`, and moves the web app off the origin the Keycloak client accepts. The API keeps both its endpoints. The method is marked for evaluation (`ASPIRECERTIFICATES001`, suppressed in the AppHost project).
- The AI service answers 401 on every route without `X-Normetry-Internal-Token`, so its health check is a custom one in `AppHost.cs` that sends the token, not `WithHttpHealthCheck`.
- Formatter: CSharpier as a local dotnet tool (`.config/dotnet-tools.json`); the hook runs it on every edited `.cs` file.
