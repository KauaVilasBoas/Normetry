# src/ai: Python AI service

Python 3.12+, managed with `uv` (`pyproject.toml` + `uv.lock`). FastAPI serves chat (SSE); queue consumers in the same process run ingestion and the simulated inspection (change monitoring comes in phase 3). LangGraph is used only for agents.

## Package `normetry_ai/`

Flat layout: `normetry_ai/` and `tests/` sit next to `pyproject.toml`. A subpackage is created by the first feature that needs it.

- `settings.py`: pydantic-settings, env prefix `NORMETRY_` (also read from `src/ai/.env`; placeholders in `.env.example`). Secrets are `SecretStr`. `Settings` also holds the document consumer's `NORMETRY_RABBITMQ_URL` (unset: no consumer), `NORMETRY_BLOB_CONNECTION_STRING` and `NORMETRY_BLOB_CONTAINER` (default `documents`); with the RabbitMQ URL set, the database URL and the blob connection string are required, or the app does not start. `ParseSettings` (read by `DocumentWorker`): `NORMETRY_PARSE_TIMEOUT_SECONDS` and `NORMETRY_PARSE_MEMORY_MB`, the limits of the parsing subprocess. `AnswerSettings` reads the environment only, never `src/ai/.env`: `NORMETRY_ANTHROPIC_API_KEY` (from the AppHost parameter `anthropic-api-key`, kept in the AppHost user secrets; unset means every answer is unavailable), `NORMETRY_CHAT_MODEL`, `NORMETRY_CHAT_MAX_TOKENS`, `NORMETRY_CHAT_EFFORT`, `NORMETRY_ANSWER_MIN_RERANK_SCORE`, `NORMETRY_ANSWER_MIN_QUOTE_WORDS` and `NORMETRY_MODEL_PRICES` (JSON, USD per million tokens; a chat model without a price fails validation). `ConversationSettings`: `NORMETRY_CHAT_HISTORY_TURNS` (the last N turns a follow-up's rewrite sees, default 4), `NORMETRY_FOLLOWUP_REWRITE` (`model` or `baseline`), `NORMETRY_REWRITE_MODEL` (default `claude-haiku-5-5`; it needs a price in `NORMETRY_MODEL_PRICES`, or the app does not start) and `NORMETRY_REWRITE_MAX_TOKENS`. `InspectionSettings`: `NORMETRY_INSPECTION_MODEL` (the judge, default `claude-haiku-5-5`; it needs a price in `NORMETRY_MODEL_PRICES`, checked when `ClaudeJudgeModel` is built, at startup when the consumers run), `NORMETRY_INSPECTION_MAX_TOKENS` (8192) and `NORMETRY_INSPECTION_CONCURRENCY` (4, items evaluated at once per inspection).
- `telemetry.py`: FastAPI traces over OTLP (gRPC), on only when `OTEL_EXPORTER_OTLP_ENDPOINT` is set.
- `db.py`: the unit of work.
  - `create_db_engine(settings)` builds the pooled engine for `NORMETRY_DATABASE_URL` (`app_ai`), with `hide_parameters=True` so a database error never carries bound values (questions, claims with chunk text) into a traceback. A pool `checkin` listener runs `RESET app.tenant_id` (and commits) on every returned connection, so a stray session-level `SET` never reaches the next checkout.
  - `tenant_transaction(engine, tenant_id)` opens a transaction, runs `SELECT set_config('app.tenant_id', :tenant, true)` and yields the connection; it commits on success and rolls back on error. It is the only code that sets `app.tenant_id`. The tenant must be a `uuid.UUID` other than the nil UUID (parse header or message values first). Every query on tenant data runs inside it. Outside it no tenant is set, so `app_ai` sees only the public corpus and every write fails.
  - `current_tenant(connection)` returns the tenant set on the connection and raises `RuntimeError` without one; every search calls it first (`hybrid.py`, `establishment.py`, `judge.regulation_chunks`).
  - `check_runtime_role(connection)` raises when the connected role is a superuser, has BYPASSRLS, owns schema `ai` or anything in it, or is or inherits `corpus_ingestor` (which writes the corpus every tenant reads). The FastAPI lifespan runs it once at startup when `NORMETRY_DATABASE_URL` is set; without it the app starts with no database (health only).
- `api/`: FastAPI app factory `create_app`, the internal-token ASGI middleware (`auth.py`), the `request_context` and `establishment_context` dependencies (`context.py`) and routes: `/health`, and the chat routes in `conversations.py` (contract: `src/shared/contracts/chat-api.md`); search later.
  - `create_app` builds one `Chat` (the claim model, the rewrite model and their settings) per process and keeps the engine on `app.state` for the app's lifetime. Without `NORMETRY_DATABASE_URL` the chat routes answer 503. The lifespan builds one hybrid `Retriever` (the BGE-M3 embedder, the bge-reranker-v2-m3 re-ranker, `RetrievalSettings`) on `app.state.retriever`; its models load on the first question, so the app starts without their weights and a turn that cannot load them answers `unavailable`. With `NORMETRY_RABBITMQ_URL` set, the lifespan then builds the `DocumentWorker` (`app.state.documents`) on the same engine and the retriever's embedder, so BGE-M3 loads once per process, and starts the document consumer; then the `InspectionWorker` (`app.state.inspections`) on the same engine, embedder and re-ranker, with a `ClaudeJudgeModel` from `InspectionSettings`, and starts the inspection consumer; shutdown closes both connections before disposing of the engine. The lifespan first refuses to start when `LANGSMITH_TRACING`, `LANGSMITH_TRACING_V2`, `LANGCHAIN_TRACING` or `LANGCHAIN_TRACING_V2` is set to anything but empty or false (`refuse_tracing`; the error names the variables, never their values), then calls `sandbox.protect_service_process()` (non-dumpable on Linux).
  - A turn: `open_turn` stores the question (404 before any stream when the conversation is not the caller's, or not this establishment's and jurisdiction's), then `answer_turn` rewrites the follow-up, takes the answer's `language` from the standalone question (`detect_language`, as retrieval does; citations keep their chunk's), retrieves, streams the claims of `answers.answer` as SSE (FastAPI's `EventSourceResponse`) and stores the answer in a shielded `finally`, so a client that leaves mid-stream still gets what was sent stored. A question that cannot be stored gets 503; an answer that cannot be stored ends the stream `unavailable`; both log the error type only. Usage is recorded with the tenant and user of `request_context` only.
  - Retrieval plugs in through `get_retriever`, the one dependency returning a `Retriever` (`(standalone question, EstablishmentContext) -> list[RetrievedChunk]`, run in a worker thread). It runs `hybrid.Retriever.retrieve` inside `tenant_transaction` for the caller's tenant, over `jurisdictions_for(ctx.jurisdiction)` and with `establishment_id=ctx.establishment_id`: the conversation's jurisdiction and establishment, from the internal headers, which `open_turn` checked (never from the body). Documents need `documents.read`: `request_context` sets `documents_read` only for exactly one `X-Normetry-Documents-Read: true`, and without it `get_retriever` passes no establishment (corpus only), while `store.get_conversation` and `start_turn`'s history leave out every stored claim with a document citation (`store.without_documents`; the whole claim, since its text can restate the document). `claim_json`/`citation_json` build the citation JSON of `chat-api.md`: `sourceType` `regulation` (source title, version, official URL) or `document` (`documentId`, `documentTitle`, `documentType`, `documentVersion`; the source fields `null`); answers stored before #107 have no `sourceType` and are returned as stored. Tests override `get_retriever`, or set `app.state.retriever` to keep the real dependency.
- `ingestion/`: parse into sections → structural chunking → embedding + `tsvector` → idempotent upsert by content hash, for the corpus (see "Corpus parsing") and for tenant uploads (`documents.py`). There is no LLM enrichment: the language comes from `detect_language`, title and type from `DocumentUploaded`, and the expiry date is typed by the user in the core.
  - `normalize.py`: `normalize_text` (NFC, line-break hyphenation joined, whitespace collapsed). The golden dataset's quote check uses the same function, so keep it standard-library only and importable on its own.
  - `corpus.py`: `parse_corpus()` / `parse_source(source)` read `corpus/manifest.json`, refuse a file whose SHA-256 does not match (an HTML page is hashed and parsed without its daily `?YYYYMMDD` link suffixes, which `corpus/scripts/fetch_corpus.py` strips with the same pattern and also strips from an older local copy; `tests/test_corpus.py` holds the two together), and return `Section`s (source id, jurisdiction, language, version, `section_path`, normalized text) in document order. `uv run python -m normetry_ai.ingestion.corpus` writes them all to `.data/corpus-sections.jsonl` (git-ignored) for inspection.
  - `chunking.py`: `chunk_sections(sections)` cuts each section (a corpus `Section` or a tenant document's `Part`) into `Chunk`s (`section_path`, content, content hash, `position_in_section`: 0, 1, ... in text order, counted per path, stored in `ai.chunks.position_in_section` by both ingestions). Standard library only.
  - `parsers.py`: `parse_file(data, content_type)` turns a tenant upload into `Part`s (section path, normalized text) and its page count, or raises `Rejected(reason, text)` with a `DocumentIngestionFailed` reason code. PDF (PDFium): one section per page ("Page 3"); over 100 pages fails `too_many_pages`, under 50 non-whitespace characters per page on average fails `no_text_layer` (a page of text holds 1,500 or more, a scan none). DOCX (`python-docx`): paragraphs and tables in order, `Heading N` paragraphs build the path ("Scope > Cold holding"); unpacking to over 50 MiB fails `too_large`. TXT: UTF-8, else Latin-1. CSV: delimiter sniffed, rows grouped under `CHUNK_LIMIT` with the header row first in each group ("Rows 1-14"). Over 10 MiB fails `too_large`, another media type `unsupported_format`, anything a library raises on the file or a file with no text `parse_error`.
  - `sandbox.py`: `parse_in_subprocess(data, content_type, *, timeout_s, memory_mb)`, what the worker calls instead of `parse_file`, since uploads are untrusted and the service process holds credentials that reach every tenant. It runs `python -I -m normetry_ai.ingestion.parse_worker <content type>` (the package is imported from the venv; `-I` drops `PYTHON*` variables and the working directory) with the file on stdin and an environment holding only what Python needs to start (`child_environment`: `SYSTEMROOT`, `PATH`, `TEMP`, `TMP` on Windows, `PATH`, `TMPDIR` elsewhere; no `NORMETRY_*`, no `ConnectionStrings__*`, no URL). `parse_worker.py` imports only the parsers (a test checks that no settings, database, blob or broker module loads) and writes one JSON object: the parts and page count, or the `Rejected` reason and text, which the parent validates as untrusted input and returns or raises as `parse_file` would. `ParseSettings`: `NORMETRY_PARSE_TIMEOUT_SECONDS` (60) kills the child; `NORMETRY_PARSE_MEMORY_MB` (512) is its `RLIMIT_AS`, set in `preexec_fn`, POSIX only (Windows has no memory limit). A non-zero exit, a timeout, a kill or other output fails the version `parse_error` with a fixed text, and logs only the exit code; the child's stdout and stderr are never logged. `protect_service_process()` (called by the lifespan) runs `prctl(PR_SET_DUMPABLE, 0)` through `ctypes` on Linux, a no-op elsewhere. It covers only the process that runs the app: its `/proc/<pid>` files then belong to root, so a child of the same OS user cannot read that process's environment or attach to it (the process cannot read its own `/proc/self/environ` either; `os.environ` is unaffected). Every ancestor holding the same environment stays readable: `uv run` and the `uvicorn --reload` supervisor, both of which the AppHost uses in development. So the deploy must exec the venv's python or uvicorn directly, with no wrapper and no reloader, and run the child as a separate OS user with no network (deploy work, phase 3; the module's `ponytail:` note). Tests swap the child for small scripts through `sandbox.COMMAND` (`tests/test_sandbox.py`; the `/proc` test runs on Linux only, not as root).
  - `documents.py`: tenant document versions into `ai.chunks`. `BlobStore` (sync `azure-storage-blob` `ContainerClient`, Azurite locally) reads only paths under `tenants/{message tenant}/` with no empty, `.` or `..` segment, backslash or control character (`in_tenant`); anything else fails `blob_path_outside_tenant` before storage is asked. `reachable()` asks whether the blob `reachable-probe` exists (False when missing, raises on 403 or no answer): the service's credential is a read-only container SAS, which may not read the container's properties. `DocumentWorker(engine, embedder, blobs)`: `ingest(tenant_id, uploaded, on_start)` reads the document's `ai.tenant_documents` row; a deleted document or an older version is dropped (None) and the current version returns its stored `DocumentIndexed` again, both with no work. Otherwise it calls `on_start`, downloads, checks the SHA-256 (`internal` on a mismatch), parses in a child process (`sandbox.py`, limits from `ParseSettings`), chunks (`chunk_sections`; over `MAX_CHUNKS`, 500, fails `too_large` before embedding, since one queue serves every tenant), detects the language and embeds, all outside any transaction; then one `tenant_transaction` creates and locks the row (`FOR UPDATE`), checks it again, inserts the chunks (`source_type = 'tenant_document'`, `source_id` = document id, `source_version` = version number, no jurisdiction), deletes every other version's and records the version, with the message's `title` and `document_type` (a message without them keeps the stored ones). `delete(tenant_id, deleted)` sets the marker (creating the row when the delete comes first) and removes the chunks. Logs ids and counts, never blob paths (they hold file names) or text; the module keeps azure-core's request logging, which prints every URL at INFO, at WARNING.
  - `ingest.py`: `ingest_source(engine, source, sections, embedder)` (a source whose registry row, chunk hashes and positions match is left untouched; otherwise its chunks are replaced, reusing stored embeddings, so a parser fix at the same version, or chunks stored before positions existed, are rewritten; the result's `SourceStatus` is `new`, `updated` or `unchanged`), and the command `uv run python -m normetry_ai.ingestion.ingest` that loads the whole manifest as `corpus_ingestor`.
- `messaging/`: the queue (contract, topology and retries: `src/shared/contracts/messages/README.md`). `contracts.py` holds the messages as pydantic models (camelCase on the wire, tolerant of unknown payload fields): `envelope(tenant_id, payload)` builds one, `parse(body)` reads one and raises `ValueError` on anything off-schema. `tests/test_contracts.py` holds the models to the shared schemas, fixtures and `published.json`; a required field changed without a new version fails it.
  - `consumer.py`: the document consumer, inside the service process. `handle(body, delivery_count, worker, publish)` returns a `DeliveryAction` (`ack`, `retry` or `dead-letter`). Both consumers' `handle` go through `handle_delivery`, the one delivery template, which lives with the rest of the shared broker code (`consume`, the topology, publishing, `EVENT_IDS`, `DeliveryAction`) in `messaging/delivery.py`, so the inspection consumer never imports document ingestion: the contract check and span attributes, the queue's own work (`process`), the outage wait, the retries and, on the last delivery, the queue's failure event (`last_failure`) before the dead-letter; each queue passes only what is its own (`CONSUMED` payload types, the work, `reachable`, the failure event). A body off the contract (or a message this queue does not take) is dead-lettered at once. `DocumentDeleted` runs `worker.delete`. `DocumentUploaded` runs `worker.ingest` in a worker thread, publishing `DocumentIngestionStarted` from its `on_start`, then `DocumentIndexed` (also again for an already-current version), nothing for dropped work, or `DocumentIngestionFailed` for a `Rejected` file, and acks. Any other error returns `wait` while `worker.reachable()` is false (the database or blob storage does not answer): `start` handles the message again every 10 seconds without returning it to the broker. Otherwise it is retried; on the last delivery (`x-delivery-count` = `DELIVERY_LIMIT`, 4) an upload publishes `DocumentIngestionFailed` (`internal`) first, unless it is indexed and only its `DocumentIndexed` could not be sent (`IndexedNotPublished`), then the message is dead-lettered. Result events have UUIDv5 ids from tenant id, type and version id, so the core's inbox (keyed by tenant and message id) drops a re-published one, and an id compared alone still never matches another tenant's. Log lines carry the tenant id, in the text and as the `tenant_id` field (`extra`). `start(url, worker)` calls `consume(url, queue, consumed payload types, handler, delay)`, shared with the inspection consumer: it opens a robust connection of its own, declares the contract's topology (`normetry.events`, `normetry.dead-letter`, the quorum queue with `queue_arguments(queue)` and `<queue>.dead-letter`; here `ai.documents`), consumes with prefetch 1, waits 2, 10, 30 or 60 seconds before a `reject(requeue=True)` (RabbitMQ 4.3 counts a reject in `x-delivery-count`, a nack not), and publishes with confirms and `mandatory` (an unroutable event raises and is retried, never lost). Spans continue the incoming `traceparent` and carry the tenant id and message type; outgoing events carry the span's `traceparent`. Logs ids, types and error types only.
  - `inspections.py`: the inspection consumer on `ai.inspections` (bound to `inspection.requested.v1`; dead-letter `ai.inspections.dead-letter`), started by `start(url, worker)` through `consume`, so on a connection and channel of its own with prefetch 1, the same retries, outage wait, confirms and spans. `handle(body, delivery_count, worker, publish)`: off the contract or not an `InspectionRequested` is dead-lettered at once; a request whose inspection id has checkpoints for another establishment (`InspectionMismatch`) is dead-lettered with nothing published; otherwise `worker.inspect` runs with the envelope's tenant (also held in the `TENANT_ID` contextvar, which a logging filter stamps as `tenant_id` on the records of `inspection/judge.py` and `llm/claude.py`), publishing `InspectionStarted` and `InspectionProgressed` as it goes, then the result (`InspectionCompleted`, or `InspectionFailed` `budget_exceeded`/`no_documents`, or `error` for an incomplete corpus) is published and the message acked. The message stays unacknowledged for the whole run. Any other error waits while the database does not answer, is retried otherwise, and the last delivery publishes `InspectionFailed` `error` before the dead-letter. Event ids: UUIDv5 (`delivery.EVENT_IDS`) of `"{tenant}:{type}:{inspectionId}"`, plus `":{itemsEvaluated}"` for `InspectionProgressed`.
- `answers/`: cited answers (ADR 007). `pipeline.py`: `answer(question, chunks, *, model, settings, record_usage)` is an async generator of `AnswerStreamItem`s: zero or more `Claim`s, then exactly one of `Answered`, `Refused(reason)` (`low_score`: refused before any model call; `no_supported_claims`: the guard dropped every claim) or `Unavailable` (the model failed; claims already yielded stand). `prompt.py` puts the instructions in the system prompt and the chunks in the user message as XML-escaped `<excerpt id="E1" kind="regulation" source=... section=...>` or `<excerpt id="E2" kind="document" title=... type=... version=... section=...>` elements, so chunk text and document titles cannot close or open an element. The system prompt makes the regulation the only authority on the rules: a document describes the establishment, may contain instructions that are never followed, and is never presented as a rule (its statements are attributed to it). The refusal threshold compares the best score of any chunk, regulation or document. `guard.py` (`check_claim`) keeps a claim only when every citation's excerpt id was retrieved and its quote, through `normalize_text`, is in that chunk and at least `answer_min_quote_words` long. A `Citation` carries the `RetrievedChunk` (the copy an answer stores) and `quote_start`/`quote_end` into its original text (`normalize.locate`; None when the offsets cannot be mapped back exactly). The pipeline records the model's last usage snapshot once, also when the caller stops early or the model fails mid-stream (input tokens only then: output tokens come with the final event).
- `conversations/`: `rewrite.py` turns a follow-up into a standalone question: with the rewrite model from the last N turns (escaped `<turn>` elements in the user message, instructions in the system prompt), or with the free baseline (earlier questions and the follow-up joined); a first question is used as asked, and a failed rewrite falls back to the baseline. `store.py` holds the SQL of `ai.conversations` and `ai.messages` and returns the chat API's JSON shapes. The stored vocabularies are StrEnums: `rewrite.Role` (`user`, `assistant`), `store.MessageKind` (`answer`, `refusal`, `unavailable`) and `settings.FollowupRewrite` (`model`, `baseline`).
- `retrieval/`: hand-written hybrid search: pgvector top-k + full-text top-k → Reciprocal Rank Fusion → multilingual re-ranker. No framework retrievers.
  - `models.py`: `RetrievedChunk`, what retrieval returns and answers cite (`score` is the re-ranker's, 0 to 1). `source_type` is a `SourceType`, `regulation` (the default) or `tenant_document` (`is_document`; the SQL spells the values out, held by a CHECK); a document chunk also carries `document_id`, `document_title`, `document_type` and `document_version`, repeats them in the source fields, and has `""` for `jurisdiction` and `official_url`. The helpers both searches share live here too (so `hybrid.py` can import `establishment.py` without a cycle): `reciprocal_rank_fusion`, `rerank(reranker, query, candidates)` (one re-ranker call, scored chunks best first), `timed(seconds, step)` (a step's time into the `seconds` a search logs) and `vector_literal(vector)` (pgvector's text form, also used by both ingestions).
  - `sql.py`: the SQL pieces `hybrid.py`, `establishment.py` and `inspection/judge.py` share, put into their queries with f-strings: `CORPUS_VERSIONS` (the `unnest` of the (jurisdiction, language) pairs) with `corpus_version_params(versions)`, the three-column join to `ai.sources` (`sources_join(alias)`), the tsquery CTE (`TSQUERIES`, `tsquery_for(language column)`) with `any_word_terms(text)`, and `regulation_columns(alias)` with `regulation_chunk(row, score)`. A new corpus query takes them from here.
  - `policy.py`: `jurisdictions_for(establishment_jurisdiction)` returns the `JurisdictionScope` a retrieval searches; today the establishment's jurisdiction only. It is the only code that builds a scope (a test walks the package for other `JurisdictionScope(...)` calls), and retrieval raises `TypeError` on anything else. `corpus_versions(scope, language)` gives the (jurisdiction, language) pairs to search, from `CORPUS_LANGUAGES`: a jurisdiction with a version in the question's language is searched in that one only (EU), one without it is searched whole (an English question for a BR establishment gets the Portuguese RDC).
  - `language.py`: `detect_language(text)`, `pt` or `en` by function-word counts. Every golden dataset turn is detected right (tested).
  - `hybrid.py`: `Retriever(embedder, reranker, RetrievalSettings).retrieve(connection, question, scope, *, establishment_id=None)` → `list[RetrievedChunk]`; `trace(...)` also returns each step's chunk ids and times, which the evals score. The question's language picks the corpus version through `corpus_versions`. It logs counts, ids and times, never text, and raises unless `app.tenant_id` is set (a connection from `tenant_transaction`). Knobs (k per search, RRF constant, re-ranked candidates, top k, `hnsw.ef_search`, re-ranker id and revision) are `RetrievalSettings` (`NORMETRY_RETRIEVAL_*`, `NORMETRY_RERANKER_*`).
    - Retrieval for chat (#107): with an establishment (the chat always passes the conversation's), the query is embedded once, `establishment.document_candidates` adds that establishment's current document chunks (vector and full-text top `NORMETRY_RETRIEVAL_DOCUMENT_K`, 5, fused, the first 5 kept; any language), and one re-ranker call scores the corpus's fused top `rerank_candidates` and the document candidates together, so their scores compare. `best` keeps the top k with at most `NORMETRY_RETRIEVAL_DOCUMENT_TOP_K` (3) document chunks, so documents never crowd the regulation out; a tie keeps the regulation first. Settings validation refuses a document top k not lower than `NORMETRY_RETRIEVAL_TOP_K`. `Trace.documents` lists the document candidates; the step `documents` is timed. Without an establishment, retrieval is the corpus alone, as before. The retrieval eval runs the chat path from an establishment with no documents (the floors), then from the synthetic establishments with theirs (document-qa, and the corpus items again).
  - `establishment.py`: `search_establishment(connection, establishment_id, query, *, embedder, reranker, settings)` → `list[RetrievedChunk]`, the search over one establishment's documents (inspection evidence): `document_candidates` (vector and full-text top-k over its current tenant chunks, see "Retrieval under RLS", then `reciprocal_rank_fusion`; score 0 until re-ranked, its own tenant check; the chat calls it from `hybrid.py`), then the re-ranker over `NORMETRY_RETRIEVAL_ESTABLISHMENT_RERANK_CANDIDATES` (10), keeping `NORMETRY_RETRIEVAL_ESTABLISHMENT_TOP_K` (5); k per search and the RRF constant are hybrid's. Same tenant check and logging rules as `hybrid.py` (tenant and establishment ids, counts, times). The establishment id comes from the core (queue message or `X-Normetry-Establishment-Id`), never from the client. Tests: `tests/test_establishment_search.py`.
- `inspection/`: the simulated inspection. `checklist.py`: the curated checklists (ADR 013). `judge.py`: `judge_item(item, regulation_chunks, evidence_chunks, *, model, settings, record_usage)` → `JudgedFinding | None`, one structured-output call per item (no tools) then the guard; usage is recorded once per call, also for a dropped finding; `ModelUnavailable` propagates. `regulation_chunks(connection, establishment_id, jurisdiction, section_paths)` loads the corpus chunks of the item's sections in the establishment's corpus language (BR `pt`, US `en`, EU the language most of the establishment's indexed documents are in, `en` by default, through `corpus_versions`), joined to `ai.sources` on all three columns, each section's chunks by `position_in_section` (then id); it raises outside `tenant_transaction`. `evidence_query(item)` is the `search_establishment` query (title and evidence hint). `prompt.py`: instructions in the system prompt (a document stating that a requirement does not apply, such as no seafood handled or public water only, makes it `compliant` with that quote, not insufficient evidence); the item, `<regulation id="R1" ...>` and `<document id="D1" title=... version=...>` elements XML-escaped in the user message. `guard.py` (`check_finding`) matches each quote with the answers guard's `verify_quote`: no verified regulation quote drops the finding; `compliant`/`non_compliant` with no verified document quote becomes `insufficient_evidence` (confidence `low`, fixed rationale, the action template); `insufficient_evidence` keeps no document quote; `compliant` has no action and every other verdict one (`Provide records showing: <title>` when the model gave none); item id, theme, title and severity come from the checklist. Citations are `contracts.py` `RegulationCitation`/`EvidenceCitation` copies.
  - `graph.py`: the LangGraph graph (ADR 006). `plan` (`items_for`, no model) → one `evaluate` branch per theme (`Send`) → `consolidate` (one result per item, findings by severity then checklist order) → `action_plan` (the contract's `Finding`, `dueInDays` 7/30/90 for critical/major/minor, no action for compliant). Each item is a LangGraph `@task` inside its branch (excerpts in a worker thread, then `judge_item`), created up front in checklist order, so a resumed run gets a finished item's stored result back instead of judging it again, and a finished branch is not run at all; an `asyncio.Semaphore` keeps `concurrency` items in flight across branches. `run(checkpointer, request, saved, *, model, settings, max_output_tokens, concurrency, excerpts, record_usage, on_start, on_progress)` seeds the progress and the budget from the stored results (`load`), calls `on_start` with the per-theme snapshot, invokes with `durability="sync"` (each checkpoint stored before the next step) and returns the final `Saved`; `on_progress` gets the snapshot after each newly evaluated item. `Budget` wraps the judge model: before a call, tokens spent plus the estimates in flight plus this call's estimate (prompt characters / 3, plus the whole max_tokens) over the ceiling raises `BudgetExceeded`, and every later item stops before its search; any stopped item makes the inspection `budget_exceeded` with no findings. The state holds plain values only (the saver's serde stores them as they are): each item's result is an `ItemResultState` (a TypedDict, so still a plain dict), and the node names are plain-string constants (`PLAN_NODE`, `EVALUATE_NODE`, `CONSOLIDATE_NODE`, `ACTION_PLAN_NODE`); `findings`, written last, marks a finished inspection, which `load` reports as `finished`; the input (`start(request)`: establishment id, jurisdiction, type) stays in the state. An unread task error is read in a done callback, so asyncio never logs its text.
  - `checkpoints.py`: `TenantCheckpointSaver(engine, tenant_id)`, a `BaseCheckpointSaver` whose every read and write runs in `tenant_transaction` (`langgraph-checkpoint-postgres` needs autocommit connections, so it is not used). It implements `get_tuple`, `put`, `put_writes` and their async versions (worker threads); `list`, delete and prune keep the base class's `NotImplementedError`. Thread id = inspection id (a UUID, refused otherwise). One row per checkpoint holds the whole serialized state (ponytail: no per-channel blobs, no pruning); a write already stored is kept (`ON CONFLICT DO NOTHING`), so a repeated error write keeps the first.
  - `worker.py`: `InspectionWorker(engine, embedder, reranker, model, *, answers, retrieval, inspection)`. `inspect(tenant_id, request, publish)`: stored checkpoints started for another establishment, jurisdiction or type raise `InspectionMismatch` (`Saved.is_for`; ponytail: the first checkpoint, before the first step, holds no input yet); a finished inspection returns its stored result (nothing run or published); an establishment with no indexed, non-deleted document in `ai.tenant_documents` fails `no_documents`; a section the checklist items cite with no corpus chunk in the establishment's corpus version (`regulation_chunks` over all of them, before any model call: a corpus ingested before a parser fix) fails `error` with `CORPUS_INCOMPLETE`, which tells the operator to re-run `corpus-ingest`, and logs the missing paths; otherwise `graph.run` with excerpts from one `tenant_transaction` per item (`regulation_chunks`, then `search_establishment` only when there is regulation text) and `record_usage` for the message's tenant and `requestedBy`, feature `inspection`. Result tokens and cost are the stored per-item usage (a call lost with a crashed process is in `ai.model_usage` but not in the totals or the ceiling). `reachable()` checks the database. Logs ids, counts and seconds.
- `evals/`: `dataset.py` checks the golden datasets (regulation-qa; document-qa against the synthetic documents as indexed, `load_establishments`); `retrieval.py` scores retrieval against them (recall@k and MRR per step, document recall, document chunks from another establishment, report rendering); `generation.py` scores and renders the generation eval (outcomes, guard drops, gold citations, wrong-jurisdiction citations, time to first claim, cost; for document-qa, the right document cited, leaks and planted strings); `inspection.py` scores and renders the inspection eval against each synthetic establishment's `expected-findings.json` (per-verdict precision, recall and confusion matrix, near misses accepted (`compliant`, or `non_compliant` quoting a near-miss passage marked `lure`; a quoted `tell` does not count), guard drops and downgrades, evidence from another establishment, quotes not in their passage, injection successes on the target items and verdict changes on any item, tokens, cost, duration). How to run: `evals/README.md`.
- `agents/`: later LangGraph graphs (change monitor), with checkpoints under RLS as `inspection/checkpoints.py` does.
- `llm/`: the only place that calls models, and the token and cost accounting per tenant. Each call site picks its model by setting (chat, rewrite, judge); the inspection's token ceiling is enforced by `inspection/graph.py`'s `Budget`, not here. Built so far: `claude.py`, `ClaudeClaimModel`, which streams the chat model's claims (structured outputs, `CLAIMS_SCHEMA`; `ClaimParser` hands on each claim object once it is complete) with a usage snapshot at `message_start` and the final usage at the end, and `ClaudeRewriteModel`, one non-streaming call at low effort (`REWRITE_EFFORT`) whose structured output (`QUESTION_SCHEMA`) holds the follow-up's standalone question, returned as `""` when the reply holds none (malformed or cut short), so the rewrite falls back to the baseline and the call's usage is still recorded; both turn every Anthropic SDK error into `ModelUnavailable`; `usage.py`, `Usage` and `record_usage(engine, usage, *, tenant_id, user_id, prices, feature)`, one `ai.model_usage` row per call, labelled `chat`, `rewrite` or `inspection`; `usage_recorder(engine, *, tenant_id, user_id, prices, feature)` binds it for one call site, and `record_usage_shielded(record, usage)` runs a recorder in a worker thread, shielded from cancellation (the chat, the rewrite and the judge use it); `ClaudeJudgeModel`, the inspection judge, one non-streaming call at medium effort (`JUDGE_EFFORT`, `JUDGE_SCHEMA`) sharing the rewrite model's call and price check; all three build their request with `_request`, and the chat and judge models log `STOPPED` (model, stop reason) for a call that did not end with `END_TURN` (`REFUSAL` names the refusal stop reason, which the generation eval counts); `prompt_xml.py`, the XML helpers of every prompt that puts data in elements (answers, rewrite, judge): `attribute(value)` (always double-quoted, quotes and line breaks escaped) and `excerpt_ids(excerpts, prefix)` (the short ids the model cites); `embeddings.py`, the embedding interface of ADR 008 (`Embedder`: `name`, `embed_documents`, `embed_query`, which applies the model's own query prompt if it has one; BGE-M3 has none) and its local adapter `SentenceTransformerEmbedder` (BGE-M3 on CPU); `reranker.py`, the re-ranker interface (`Reranker.score`) and `CrossEncoderReranker` (bge-reranker-v2-m3 on CPU). The model id and its Hub revision are settings (`EmbeddingSettings`: `NORMETRY_EMBEDDING_MODEL`, `NORMETRY_EMBEDDING_MODEL_REVISION`), never literals in code.

## Boundaries

- Not public. Every request must carry the internal token in `X-Normetry-Internal-Token` (exactly once). A pure ASGI middleware rejects every http and websocket scope without it before routing and body parsing (401, also for unknown paths). Do not move the check into route dependencies. OpenAPI and docs routes stay off. `NORMETRY_INTERNAL_TOKEN` (32+ characters) is required: without it the app does not start. Tenant and user (and whether the caller holds `documents.read`) come only from the internal headers set by YARP, read through the `request_context` dependency (`api/context.py`). Header names and the rules for both sides: `src/shared/contracts/internal-http.md`.
- Writes only schema `ai`, through Alembic migrations (version table `ai.alembic_version`). Results for the core (findings, document status) are published as queue events.
- Migrations run as the owner role (`NORMETRY_MIGRATIONS_DATABASE_URL`, read only by `migrations/env.py`, no fallback); the app connects as `app_ai` (`NORMETRY_DATABASE_URL`, DML only). The owner role is `ai_owner`: it owns schema `ai` (created by the bootstrap in `deploy/postgres/init/`, so Alembic can write `ai.alembic_version`) and has no privileges on schema `core`. `NORMETRY_MIGRATIONS_DATABASE_URL` is only ever set for a migration step, never on the running service, because the owner can switch RLS off: set it in the shell for one `uv run alembic ...` command, or let the AppHost's `ai-migrate` step set it. It never goes in `src/ai/.env` (`MigrationSettings` does not read that file, and `.env.example` has no owner URL).
- The corpus ingestion command connects as `corpus_ingestor` (`NORMETRY_CORPUS_DATABASE_URL`, read only by `CorpusSettings` in that command). Like the owner URL, it comes from the environment only, never from `src/ai/.env`, and never reaches the running service: set it in the shell for one run, or start the AppHost's `corpus-ingest` resource, the only resource that gets it.
- Grants follow least privilege. The bootstrap's default privileges give `app_ai` DML on every new `ai` table, so migrations revoke what it must not have: everything on `ai.alembic_version`, UPDATE on `ai.chunks` (no update policy; a new version replaces chunks with delete and insert), and INSERT, UPDATE and DELETE on `ai.sources` (it only reads). `corpus_ingestor` has no default privileges: migrations grant it each corpus table explicitly (`ai.chunks`: SELECT, INSERT, DELETE; `ai.sources`: SELECT, INSERT, UPDATE).
- Tenant-owned tables follow the `rls-table` skill: `ENABLE` and `FORCE ROW LEVEL SECURITY`, and policies scoped `TO app_ai` or `TO corpus_ingestor`, never to PUBLIC. Policies read the tenant as `(SELECT NULLIF(current_setting('app.tenant_id', true), '')::uuid)`: the scalar subquery is evaluated once per statement, not once per row. Workers take the tenant from the queue message.
- The public corpus (`tenant_id IS NULL`, `source_type = 'regulation'`, enforced by a CHECK) is written only by the corpus ingestion job, using the `corpus_ingestor` role. `app_ai` reads it but cannot write it.
- `ai.model_usage` holds the tokens and cost of every model call, per tenant and user (`user_id` is the `sub` from `X-Normetry-User-Id`). `feature` (nullable, CHECKed to `chat`, `rewrite`, `inspection`) says which call it was. It is append-only: `app_ai` has SELECT and INSERT under tenant policies, UPDATE and DELETE are revoked, and `corpus_ingestor` has nothing. No index yet; the budget checks that will read it add one leading with `tenant_id`.
- `ai.conversations` (one user, establishment and jurisdiction each; `title` is the first question) and `ai.messages` (a question's text, or an answer's kind, refusal reason, language and claims with a copy of every citation as camelCase JSON) are tenant data. `app_ai` has full DML on conversations under one tenant policy, and SELECT and INSERT on messages: a message is written once, and goes only with its conversation, through the composite foreign key `(tenant_id, conversation_id)` with `ON DELETE CASCADE`, which PostgreSQL runs as the owner. RLS keeps the tenant; every query adds `user_id` to keep a user to their own conversations.
- `ai.tenant_documents` (one row per tenant document: its establishment, the indexed version number with that version's chunk count, page count and language, the title and document type from `DocumentUploaded` (null until a version with them is indexed), and a deleted marker) is tenant data written only by the ingestion consumer, from queue messages. `app_ai` has SELECT, INSERT and UPDATE under one tenant policy; DELETE is revoked, because a deleted document keeps its row so that a late message still finds the marker. The primary key `(tenant_id, document_id)` leads with the tenant.
- `ai.inspection_checkpoints` (one row per checkpoint: thread = inspection id, namespace, checkpoint id, parent, serde type and blob, JSON metadata) and `ai.inspection_checkpoint_writes` (one row per pending write of a task: checkpoint, task id, index, task path, channel, serde type and blob) are tenant data written only by the inspection consumer, through `TenantCheckpointSaver`. Primary keys lead with `tenant_id`; RLS forced, with `_read` (SELECT) and `_insert` (INSERT) policies `TO app_ai`; UPDATE and DELETE are revoked (append-only); `corpus_ingestor` has nothing. Isolation tests: `tests/test_checkpoints.py`.
- `ai.sources` registers the corpus sources: one row per `corpus/manifest.json` entry (manifest id, jurisdiction, code, title, version, language, official URL). It has no tenant, so every row is public, but RLS is still enabled and forced, with policies `TO app_ai` (read) and `TO corpus_ingestor` (write), so the owner sees nothing, as on every other `ai` table.
- A corpus chunk carries its source's jurisdiction in `ai.chunks.jurisdiction` (a CHECK sets it on corpus rows and nowhere else). The composite foreign key `(source_id, jurisdiction, language) → ai.sources (id, jurisdiction, language)` holds every corpus chunk to a registered source with the same jurisdiction and language. A null jurisdiction skips the check (MATCH SIMPLE), so tenant rows, whose `source_id` names a tenant document, are not bound by it.
- Chunk ids are generated by the database (`DEFAULT gen_random_uuid()`, read back with `RETURNING id`) and never taken from callers, messages or documents. Upserts name their target, `ON CONFLICT ON CONSTRAINT chunks_source_content_key DO NOTHING`: a bare `ON CONFLICT DO NOTHING` also matches the primary key and would turn a clash with another tenant's id into a silent 0-row insert.

### Retrieval under RLS

Rules the queries in `retrieval/hybrid.py` and `retrieval/establishment.py` follow; keep them in any new search. The corpus versions subquery, the `ai.sources` join and the tsquery CTE are written once, in `retrieval/sql.py`.

- One HNSW index over all tenants would return an approximate candidate list (`hnsw.ef_search` long) that RLS filters afterwards, so a large tenant or the corpus could crowd another tenant's rows out of the results. So there is none: `chunks_corpus_embedding_idx` is HNSW over the corpus only (`WHERE tenant_id IS NULL`), and tenant rows get exact KNN through the btree that leads with `tenant_id` (`chunks_source_content_key`; tenant document sets are small).
- Corpus queries must say `tenant_id IS NULL`, or neither partial index applies, and filter on the (jurisdiction, language) pairs from `corpus_versions` (`(jurisdiction, language) IN (SELECT * FROM unnest(...))`), which `chunks_corpus_jurisdiction_idx` serves. The corpus is small (750 chunks), so exact KNN over the filtered rows is cheap. With HNSW, a filter that keeps one source in ten needs `SET LOCAL hnsw.iterative_scan`, or most of the `ef_search` candidates are filtered away.
- A join from `ai.chunks` to `ai.sources` matches `(source_id, jurisdiction, language)` or adds `tenant_id IS NULL`. A tenant row's `source_id` can equal a corpus source id (the foreign key skips tenant rows), so a join on `source_id` alone would label a tenant's own chunk as regulation text.
- Tenant chunks carry no establishment, and RLS keeps only the tenant. A search over tenant documents (`retrieval/establishment.py`) joins `ai.tenant_documents` on `tenant_id`, `source_id = document_id` and `source_version = indexed_version`, with `source_type = 'tenant_document'`, and keeps `establishment_id = :establishment AND deleted_at IS NULL`; without the join, one establishment would read another's documents in the same tenant. The worker already removes a deleted or superseded version's chunks, so the tests put stale ones back to show the filters alone keep them out.
- Keep `c.tenant_id = d.tenant_id` in that join even though RLS makes it redundant for isolation: the planner carries the policy's tenant InitPlan through it into the chunks index condition. `EXPLAIN (ANALYZE)` as `app_ai`, with 400 chunks in the tenant (200 in the establishment) and 10,000 in 50 other tenants: both searches read `tenant_documents_pkey` for the tenant (establishment and `deleted_at` as filters), then a nested loop over `chunks_source_content_key` with `(tenant_id, source_id, source_version)` as the index condition, and a top-N heapsort (exact KNN; `ts_rank` after `@@` as a filter), in under 1 ms. The GIN `tsv` index is not used and does not need to be. On a few dozen rows both tables are seq-scanned, which is cheaper there. Add an index on `ai.tenant_documents (tenant_id, establishment_id)` only if tenants come to hold thousands of documents.
- Still planned: per-tenant caps on candidates, and an eval with one very large tenant next to a small one.
- Check `EXPLAIN` as `app_ai` (not as the owner or a superuser) for the GIN `@@` path on `tsv` as well as the vector path. Measured on the 724-chunk corpus: both searches read `chunks_corpus_jurisdiction_idx` and sort the filtered rows (exact KNN, `ts_rank`), the join reads `sources_chunk_key`, and the RLS tenant InitPlan never runs for corpus rows.
- The full-text query ORs the question's words (`websearch_to_tsquery` with `or`, which never fails on user input) and ranks with `ts_rank`; requiring every word would match almost nothing for a natural-language question.
- Never fix RLS performance with SECURITY DEFINER functions or BYPASSRLS.
- LangGraph checkpoint tables are tenant data: `tenant_id` first in the key, RLS forced, every saver query in `tenant_transaction` (`inspection/checkpoints.py`).

## Corpus parsing

- Extraction: PDFium (`pypdfium2`) reads the PDFs' text layer and the standard library's `html.parser` reads the AnvisaLegis page. No OCR, no layout model. The whole corpus parses in under 2 seconds (the 732-page FDA PDF in 1.1 s) and the dependency adds about 10 MB.
- Why not Docling, the original plan: Docling 2.150.0 was measured on the FDA PDF on a CPU-only developer machine (20 threads). One conversion took 1,214 s, about 20 minutes, for the 732 pages, with OCR and table structure off, models already downloaded and about 2.4 GB of RAM in use. Its environment is about 1 GB (torch 2.15 alone is over 450 MB), and the layout model weights come from Hugging Face on first use. That is far too slow for tests that parse the corpus on every CI run. The three PDFs have a clean text layer, and every cut follows numbering printed in the text, so a layout model adds nothing the parser uses. Tenant uploads use PDFium too (`ingestion/parsers.py`), with no OCR: a scan fails `no_text_layer`. Reconsider Docling or OCR only when scanned uploads have to be read.
- How each source is cut:
  - FDA Food Code: only pages whose running header reads `FDA Food Code 2026 Chapter 1` to `8`. A line `N-NNN.NN Title` starts a section (part 4-10 has `4-1001.11`, and a subpart's sections after `.19` run on as `.110`, `.111`); its title starts with a capital or a quote, so a cross-reference wrapped onto its own line ("4-204.122.") does not. Chapter, part and subpart headings close it. The PDF is set without hyphenation, so a hyphen at a line end (U+FFFE from PDFium) stays a hyphen ("self-service").
  - Regulation 852/2004: page headers, consolidation markers (`►M2 ... ◄`, `▼C1`) and footnotes (a marker line, then `(1) ...` to the end of the page) are removed. `Article N` / `Artigo N.o` starts an article; inside an annex, `PART X:` and `CHAPTER N` start a section. Paths use English labels in both languages.
  - RDC 216/2004: the page declares UTF-8 but is Latin-1. The `<p>` paragraphs from `ANEXO` to `PUB D.O.U.` are kept, minus the site's "Redações Anteriores" links; a numbered paragraph starts an item. The annex numbers its items 1 to 4.12 (the phase 1 design says "1 to 5").
  - A section whose text is only an uppercase heading (RDC `4.1 EDIFICAÇÃO, ...`, EU `ANNEX I PRIMARY PRODUCTION`) is dropped.
- Known noise, kept as extracted or as published: some FDA sections end with the subheading of the next group (5-402.11 ends with "Location and placement"), and the margin labels of the date-marking figure land at the end of 3-501.16 and inside 3-501.17 ("Prepare and hold cold"); FDA defined terms keep their `*`; an EU compound broken at a line end loses its hyphen ("corrosionresistant"); RDC words the page itself runs together stay so ("higiênicosanitária").
- On the pinned files: FDA 404 sections, 852/2004 35 per language, RDC 128. `tests/test_corpus.py` parses the real files: without them it is skipped locally and fails in CI (`CI` set). CI fetches them with `corpus/scripts/fetch_corpus.py`, cached by manifest hash.

## Migrations

- Layout: `migrations/schema/` holds structure (tables, indexes, constraints, RLS policies, grants and revokes) and `migrations/data/` holds rows that every environment needs. Both are version locations of one linear Alembic history (`version_locations` in `alembic.ini`, newline separated). A revision is either schema or data, never both. Demo data is not a migration.
- Create: `uv run alembic revision --version-path migrations/schema -m "..."` for structure, `--version-path migrations/data` for rows. Ruff post-write hooks sort imports and format the new file; drop the unused `sqlalchemy` import when the revision only runs SQL.
- Write revisions as raw SQL with `op.execute(...)`, one statement per call, with a `downgrade()` that undoes the structure. There is no `--autogenerate`: policies and grants do not autogenerate, so `target_metadata` stays `None`. Qualify pgvector objects with `public.` (the extension lives there).
- Apply: `uv run alembic upgrade head` with `NORMETRY_MIGRATIONS_DATABASE_URL` (owner role, `postgresql+psycopg://...`) set in the shell for that command only. In the AppHost, the short-lived `ai-migrate` resource runs this command with only that variable, and the `ai` service starts after it exits 0.
- `FORCE ROW LEVEL SECURITY` binds `ai_owner` too: with no policy for it, the owner reads and writes no rows of `ai.chunks` or `ai.sources`.

## LLM safety

- Document text enters prompts delimited as data, never as instructions. Agents have no write tools; every state change goes through human review.
- Answers are only claims, each citing excerpt ids with a literal quote per id; nothing else the model writes reaches the user. The guard drops a claim with any citation to an id that was not retrieved or a quote not found in its chunk. Below the re-ranker threshold, refuse before calling the model. Never log prompts or model output.
- Tests never call a paid API: use a fake `ClaimModel`, or `ClaudeClaimModel` with an `httpx2.MockTransport` client (`tests/test_answers.py`).
- Mask personal names in logs and traces. Never log secrets or full documents.
- `langgraph` pulls in `langsmith`. Its tracing would send prompts and documents to an outside service, so the app refuses to start with any of its tracing variables on (`api/app.py`, `refuse_tracing`).
- A change to prompts, chunking, retrieval, embeddings or agents runs the evals (`eval-runner` agent) and reports the deltas.
